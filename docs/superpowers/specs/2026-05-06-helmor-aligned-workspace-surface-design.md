# Phase A.1: Helmor-Aligned Workspace Surface — Design

**Status:** Draft for implementation
**Date:** 2026-05-06
**Phase:** A.1 (product surface on top of the Phase A workspace foundation)
**Predecessor:** `docs/superpowers/specs/2026-04-30-workspace-and-command-center-design.md`

---

## Goal

Move Gate from "workspace as a repository-backed session container" toward "workspace as a task and delivery unit." The user should be able to enter a workspace, describe what should be built, run one or more AI CLI sessions against the correct branch/worktree, inspect changes, run scripts, and push the work toward review without losing Gate's browser-over-SSH deployment model.

Helmor is the product reference for the shape of the workflow: repository/workspace rows grouped by status, a central start composer, contextual side panels, run/change/terminal inspection, and delivery actions. Gate must adapt those ideas to remote servers and responsive web layouts rather than copying Helmor's desktop/Tauri implementation.

## Non-Goals

- Replacing Gate's SSH/WebSocket architecture with a local desktop runtime.
- Implementing full multi-agent delegation, skills, scheduled tasks, or MCP management.
- Building a full file editor or Monaco surface in this phase.
- Supporting every forge provider. GitHub via `gh` is enough for v1 when available on the remote.
- Making authentication or multi-user authorization changes.

## Product Principles

1. **Workspace is the unit of work.** A session is an execution thread inside the workspace, not the product's top-level object.
2. **Status is visible before chat.** Users should see what is running, what needs review, and what is done without opening each chat.
3. **Starting work is a first-class workflow.** Empty workspaces should lead with a composer and branch/worktree choices, not an empty session list.
4. **Delivery actions stay attached to the workspace.** Commit, push, PR, and review state should be visible in the workspace inspector even when generated by a hidden action session.
5. **Mobile remains primary.** The same workflow must degrade to sheets and stacked surfaces without hiding critical state.

## Conceptual Model Updates

Phase A model:

```text
Server
 └─ Workspace
     └─ Session
```

Phase A.1 product model:

```text
Server
 └─ Workspace
     ├─ Goal / status / branch / delivery metadata
     ├─ Sessions
     │   ├─ Primary chat session
     │   └─ Hidden action sessions
     ├─ Changes / PR state
     └─ Scripts / terminal-like command runs
```

## Workspace Status

Add a workspace-level status:

```ts
type WorkspaceStatus =
  | 'backlog'
  | 'in-progress'
  | 'review'
  | 'done'
  | 'canceled';
```

Initial rules:

- New workspace created without a prompt: `backlog`
- New session created from Workspace Start composer: `in-progress`
- PR created or opened: `review`
- PR merged or user marks complete: `done`
- User cancels/archives abandoned work: `canceled`

Status is user-editable from the Command Center row menu and Workspace Inspector. Automatic transitions are best-effort and should never block manual override.

## Data Model Changes

### `workspaces`

Add columns:

| Column | Type | Notes |
| --- | --- | --- |
| `status` | TEXT | `WorkspaceStatus`, default `backlog` |
| `goal` | TEXT NULL | Last explicit user goal from Workspace Start |
| `pinned_at` | INTEGER NULL | Sorts pinned workspaces first |
| `archived_at` | INTEGER NULL | Soft archive; hidden from primary groups |
| `primary_session_id` | TEXT NULL | Preferred visible chat session |
| `pr_url` | TEXT NULL | Current branch PR URL when known |
| `pr_state` | TEXT NULL | `none/open/closed/merged/unknown` |

### `sessions`

Add columns:

| Column | Type | Notes |
| --- | --- | --- |
| `is_hidden` | INTEGER | Hidden sessions do not appear as normal chat threads |
| `action_kind` | TEXT NULL | `commit`, `push`, `create-pr`, `review`, `fix`, etc. |
| `unread_count` | INTEGER | Workspace/sidebar badge source |

Hidden action sessions let Gate use the same provider infrastructure for delivery tasks without polluting the user's primary chat list.

## WebSocket Protocol Additions

Client -> server:

- `set-workspace-status` `{ workspaceId, status }`
- `pin-workspace` `{ workspaceId, pinned }`
- `archive-workspace` `{ workspaceId }`
- `restore-workspace` `{ workspaceId }`
- `start-workspace-task` `{ workspaceId, goal, provider?, branchMode?, branchName?, worktreeMode? }`
- `run-workspace-action` `{ workspaceId, action, prompt?, options? }`
- `fetch-workspace-inspector` `{ workspaceId }`

Server -> client:

- `workspace-inspector` `{ workspaceId, changes, pr, scripts, actionStatus }`
- `workspace-action-result` `{ workspaceId, action, status, sessionId?, error? }`
- Existing `workspace-update` carries the new fields and aggregates.

## Command Center

Replace the Phase A grid-first Command Center with a grouped work queue.

Groups:

- Pinned
- In Progress
- Review
- Backlog
- Done
- Canceled / Archived

Each row/card shows:

- Workspace name, server, repo path basename
- Status badge
- Current branch/default branch
- Active run indicator
- Primary session title or last goal
- Dirty file count
- PR badge/link when known
- Last user message/activity
- Row actions: start/continue, status change, pin, archive/delete

Desktop should prefer dense rows or compact cards; mobile can keep card rows inside the existing workspace sheet.

## Workspace Start Surface

When a workspace is selected and no session is auto-opened, the center should lead with a start composer:

- Prompt textarea: "What should we build/change?"
- Provider/model selector using existing provider support
- Branch picker:
  - current/default branch
  - create branch
  - use existing branch
- Worktree mode:
  - main checkout
  - create isolated worktree
  - use existing worktree when known
- Submit creates or continues the primary session and sends the goal.

The sessions/worktrees list remains available below or in a secondary tab, but it is not the hero content.

## Workspace Inspector

The right panel becomes workspace-aware. It should still work when a chat session is active, but its data source is the workspace.

Tabs:

- **Changes**: dirty files, diff entry points, branch, remote, PR badge.
- **Plan**: existing extracted plan for the active/primary session.
- **Run**: configured setup/run/test scripts and latest command output.
- **Terminal**: lightweight command runner over SSH. A full persistent terminal can be deferred if needed.

On mobile, the inspector uses the existing bottom sheet and tabbed sections.

## Delivery Actions

Minimum v1 actions:

- Commit
- Push
- Create PR
- Open PR
- Mark review/done/canceled

Implementation rules:

- If the action is deterministic Git/forge work, run it in `ssh-manager` directly.
- If the action benefits from AI assistance, create a hidden action session with `action_kind`.
- Action results update `workspace.pr_url`, `workspace.pr_state`, and `workspace.status` when appropriate.
- Failures must be visible in the inspector and not silently disappear into chat history.

## Repo Scripts

Introduce optional remote repo config, tentatively `gate.json`:

```json
{
  "scripts": {
    "setup": "npm install",
    "run": "npm run dev",
    "test": "npm test"
  }
}
```

Script execution runs on the remote server in the workspace root. Output is streamed to the Run tab and can be summarized into chat when requested.

## UX Flows

### Start New Work

1. User opens Command Center.
2. Selects a backlog workspace.
3. Workspace Start composer asks for the goal.
4. User picks/create branch and worktree mode.
5. Gate creates a session, marks workspace `in-progress`, and sends the goal.

### Review Work

1. Agent finishes a turn.
2. Inspector refreshes Changes and PR state.
3. Dirty files or PR state moves workspace into `review` when appropriate.
4. User opens diff/changes, runs tests, commits, pushes, creates PR.

### Continue From Mobile

1. User opens Gate on phone.
2. Command Center shows in-progress/review rows first.
3. Tap row -> chat opens, inspector is available as bottom sheet.
4. Delivery actions remain reachable without desktop-only affordances.

## Testing Plan

Server:

- Workspace status CRUD and archive/restore behavior.
- Hidden action session creation and filtering.
- `run-workspace-action` success/failure paths.
- `gate.json` script parsing with missing/invalid file fallback.

Client:

- Command Center groups and sorts by status/pin/activity.
- Workspace Start composer creates sessions with workspace context.
- Inspector renders workspace-level changes independent of selected session.
- Mobile sheet layout exposes Start, Changes, Plan, and actions.

## Open Questions

- Should each workspace have exactly one primary session, or can the user promote any visible session to primary?
- Should branch/worktree creation be explicit in the UI before session creation, or inferred from the first prompt?
- How much of PR state should be stored versus fetched live through `gh`?
- Is `gate.json` enough, or should scripts also be configurable in workspace settings?
